# Current HYPER closure: exact finite declared operand cone

Verifier Standard (VSTD) uses HYPER for a named relational composition of
admitted objects. This candidate registers exactly one objective under semantic
namespace `verifier-current-object-obligations-1`: `HYPER-4.1`, the first
dimensionless objective in current tier 4 (closure). Legacy `HYPER-4.1` under
`verifier-domain-obligations-1` remains the separate **Saturation** obligation;
no old result is relabeled, migrated or accepted as a current certificate.

## Exact proposition and boundary

For the independently selected HYPER object and expected finite collection
commitment, the retained canonical namespace records are exactly the transitive
closure of its declared named operand references, including the HYPER root: each
referenced object occurs once with its exact bytes and admitted kind, each
declared edge resolves inside that collection, no composition dependency cycle
occurs, no unrelated record is included, and the recomputed canonical
closure-member commitment equals the externally selected expected commitment.

This is **finite declared operand closure**. The algorithm follows only the
`NamespaceObject.operands` relation in retained records. A payload may describe
undeclared dependencies; neither the checker nor a Secure Hash Algorithm
256-bit (SHA-256) digest discovers them. PASS says nothing about completeness of
the represented world, mathematical proof closure, physical containment,
authenticity, ownership, privacy, consent, governance, or authority. It does
not establish all of HYPER tier 4 or any object profile. A HYPER can contain
mixed object kinds, but its PASS does not create separate kind-specific tier-4
certificates. A one-record primitive would not test this relational objective.

## Retention and replay

The request binds the semantic namespace, `HYPER-4.1` coordinate, exact
proposition-registration digest, root identifier and object digest, complete
collection digest, expected canonical member commitment, a content-addressed
evidence reference, external policy digest, and finite count, byte and operation
bounds. The policy names one installed built-in mechanism digest and sorted
nonblank trust-root labels. Labels identify the caller's assumption; neither
policy construction nor the certificate authenticates their issuer.

The builder first captures exact built-in containers and immutable namespace
records within bounds, then retains the canonical JavaScript Object Notation
(JSON) collection bytes. The mechanism reconstructs each record, reruns finite
typed composition, resolves the exact HYPER root, traverses all named operand
edges and compares the visited record set with the complete retained inventory.
Every `{object_id, object_digest}` member is sorted by identifier and hashed
with the root and member-schema version. Ordered operand targets remain inside
the underlying object digests. The full result and evidence bytes are retained
in a canonical certificate; its own digest is only an integrity check.

Offline replay requires independently supplied expected request and policy,
imports the embedded exact evidence bytes, reruns the installed mechanism and
compares every canonical certificate byte. A changed result with a recomputed
certificate digest cannot pass. Missing expected selection or retained evidence
remains UNKNOWN; an explicit mismatch, malformed record, extra object, dangling
edge, dependency cycle, or internally inconsistent typed graph FAILS. If input
exceeds a pre-capture bound, no certificate is issued and the state is
unavailable/UNKNOWN. Counts and operation budgets are dimensionless; byte
budgets count encoded or retained bytes. Input encoding uses Unicode
Transformation Format, 8-bit (UTF-8). Nothing loads submitted executable code.

The certificate contains full payload bytes, which may contain sensitive
HUMAN, IDENTITY, TOKEN, or other material. Building or replaying it is local
computational evidence, not permission to emit it. No privacy-preserving
redaction, recipient authentication, consent, governance, or controlled export
mechanism is provided here; any release needs separate action-time admission
and a verifier for the actual emitted form. The result keeps
`hyper_tier_4_conformance`, `object_profile_conformance`, `privacy`, `consent`,
`governance`, and `authority` at `NOT_ESTABLISHED` on every outcome.
