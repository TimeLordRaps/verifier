# Core Security-9 requirement selection

Private specification correction, version 1. This document specifies how the
nine-core application profile retains Security-9 requirements. It does not create
a new security proposition, a universal composed-security prerequisite, or a PASS.

The selected nine-tier architecture asks, for each object, which explicitly bounded
adversarial or failure conditions must be protected and which trusted mechanism
detects or refuses a violation. Every registered security objective therefore needs
its own threat model, trusted roots, scope, mechanism and falsifier. A hash,
signature or parser result alone is insufficient. Current per-object Security-9
propositions are not declared complete by that architecture.

The installed source does completely enumerate its narrower route registry: 26
Security-9 cells contain 29 distinct registered native route definitions. This is an
implementation denominator, not a claim that those definitions exhaust security
meaning or that every route applies to a selected application. Required-instance,
child and interaction denominators remain properties of the exact independently
selected application scope.

## Selection and conservation

For each of the 26 admitted object kinds, the core application requirements contain
exactly one rank-9 `SECURITY` family row. The row's objective census is either:

- `COMPLETE`, with a nonempty exact list of every independently selected applicable
  native requirement instance; or
- `UNKNOWN`, which grants no inference of inapplicability, completeness or PASS.

Each instance binds its object identifier (ID) and kind, operation, instruction, context,
generation, core rank 9, semantic family, objective, proposition, request, checker
policy, shard and native node. The core route admits current-family coordinates at
their named rank only. A ten-tier Security-6 or Corrigibility-10 certificate cannot
be relabelled or counted at core Security-9.

## Native children and interactions

A selected native security objective is only its published bounded proposition.
Its complete dependency directed acyclic graph (DAG) children must be selected and replayed under their exact
requests, policies, certificates and retained artifacts. A missing child, unavailable
checker or exhausted supported bound remains `UNKNOWN`, unless an independently
decidable contradiction is present; a known refutation remains `FAIL`.

Cross-object, cross-operation or other interaction security requirements are not
inferred absent. When applicable they must appear as explicit selected requirement
instances or native dependency nodes. Until their applicability and complete set are
independently established, the affected Security-9 family census remains `UNKNOWN`.
A passing subject association, issuer signature, hash or neighboring family cannot
silently discharge an unselected interaction.
Likewise, a selected child or interaction whose own required status is `UNKNOWN`
keeps its corresponding census unresolved; a parent `COMPLETE` label cannot promote
that applicability uncertainty.

## Source and mechanism binding

Application assessment requires independent exact selection and mechanism pins.
The application mechanism binds this document, the core application and progression
modules, the executed DAG helper and their named dependencies. Each native instance
also binds its registered proposition, mechanism, request, policy, certificate and
artifact bytes. Missing external pins remain `UNKNOWN`; substituted selected bytes,
source-bound mechanism digests or carried assessments are refused. Recheck recomputes
the complete selected assessment.

## Verdict boundary

Known structural, binding or native refutation is `FAIL`. Otherwise any unknown
Security-9 census, required child, applicable interaction, native replay or external
pin is `UNKNOWN` and cannot authorize release. A finite native `PASS` establishes
only its exact registered proposition. It does not establish whole Security-9,
whole-object conformance, universal composition, authority, key custody, trusted
time, live revocation, actual execution, acceptance or production admission.

Existing record, archive, source, shard, node, edge, certificate, evidence and total
byte limits remain capacities rather than completeness denominators. Capacity
exhaustion is `UNKNOWN` unless an already inspectable contradiction requires `FAIL`.
