# Source-native Tier-3 Statics

Verifier Standard (VSTD) exposes these diagnostics explicitly with
`vstd polish 3 --native-specimens --source-root . --json`.
Without `--native-specimens`, the command evaluates the root `objects.vstd`
[package GRAPH](PACKAGE_POLISH.md), not this specimen-only contract.
The separate report contract is `verifier-self-polish-statics-assessment-1`;
Tier-1 and Tier-2 report contracts retain their existing meanings.

## Selection and reasons

This fixed profile freshly executes repository admission (Tier 0), full bounded
Facets (Tier 1), fresh-source Dynamics (Tier 2), then Statics. It accepts no
retained report, signatory assertion, caller verdict, external application
selection or claimed exclusion. Passing prior reports are included in full with
their digest chains, not treated as authority merely because they say PASS.
Every numbered result must bind the same newly captured source coordinate;
source is recaptured again after execution. Cancellation yields UNKNOWN.

Statics selects all 26 installed kind cells, exactly 31 route memberships and
93 canonically ordered positive, malformed-bound negative and absent-evidence
controls. Each membership is independently matched to the installed objective
catalog and source-owned specimen registry. Its reason names why that particular
proposition needs checking, why it applies to this selected request, how the
native replay fulfills it, and what it does not establish. All 31 are necessary
within this explicitly selected union; no optional obligations or exclusions
are introduced. This is not universal applicability for arbitrary repositories.

Both builder and rechecker must belong to the imported package and match the
selected source bytes. All installed Python module bytes, including native
dependencies, are compared with the selected checkout before and after Statics.
A byte-identical isolated wheel can run the same profile. The local interpreter,
import machinery, standard library and operating system are trusted; matching
files is not execution attestation. Only the separate fresh SIM resource variant
uses its source-compiling child-execution protocol.

Each native result is retained, together with request, policy, evidence,
certificate and result digests. Positive UNKNOWN remains UNKNOWN and blocks
Tier-3 PASS. A mismatched negative or unavailable control is FAIL. Missing
runtime resources are UNKNOWN, preserving any already observed refutation.
Native certificate prerequisites are replayed by their own installed checkers.
The cumulative prerequisite is fixed by the profile, not an inferred complete
application dependency graph. Report output is bounded to 32 MiB (mebibytes).

## Important object-specific boundaries

- `SIM:SIM-3.4` reproduces an exact selected SIM-to-distinct-law OBJECT statement
  relation. Physical law truth, dimensional correctness, physical applicability,
  historical simulation correspondence and law independence are not established.
- `MODEL:MODEL-3.2` freshly observes a selected dense-model workload exhausting
  one enforced Windows committed-memory cap and completing under a larger cap.
  An unavailable Windows Job Object backend blocks PASS; it is not an exemption.
  This is not a universal minimum, authenticated physical device or portable
  cross-runtime result. No memory cap or tolerance is widened by this profile.
- The Dynamics prerequisite retains the fresh-execution `SIM:SIM-2.4` variant.
  Historical signed resource records do not acquire execution provenance.

Independent application authority is conditional on an external adoption or
semantic-completeness claim. That condition is explicitly not triggered by this
fixed source-native profile: none is claimed. Its fulfillment remains
NOT_ESTABLISHED, not silently PASS. Native authority checks inside individual
contracts remain required. Full-application status remains UNKNOWN; polished,
release-authorized and deployment-authorized remain false, even on Tier-3 PASS.

Prepared Tier-4 through Tier-9 extensions are not selected or promoted. Existing
prepared-extension receipts retain their PREPARED_NOT_INSTALLED meaning; this
profile separately installs and freshly validates only the Tier-3 selection.
