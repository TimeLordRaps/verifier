# Application release consumer

Verifier Standard (VSTD); application programming interface (API); command-line
interface (CLI); JavaScript Object Notation (JSON); directed acyclic graph (DAG);
Secure Hash Algorithm 256-bit (SHA-256); mebibytes (MiB); identifier (ID).

This opt-in consumer binds an actual application record, selected member and source
bytes, operation/context declarations and required native-instance shards. The
required release gate remains full ten-tier self-polish. Version1 evaluates finite
bindings and registered native replay; it does not implement complete applicability
authority, public checking, composed security, the complete corrigibility family or
acceptance. These separate mandatory gates remain UNKNOWN and deny release. No
finite PASS, census label, source count or arbitrary rank10 node can waive them.

Existing polish contracts1/2, nine-tier namespace meanings and current-object
semantic1 retain their meanings. The new interfaces are `vstd polish application
assess/check` and `verifier.runtime.application_release`. Recheck recomputes exact
inputs and compares the complete assessment; it never consumes a carried verdict.
No artifact installation, producer operation, publication or remote action occurs.

The selected root is a canonical zero-operand VERIFIER record. A separate HYPER
membership envelope binds finite relationships without adding operand roles to
the historical VERIFIER contract. Its `application` role names exactly that root;
other roles conserve every selected member. The root commits to the canonical
map of member IDs to record digests, excluding the root and envelope themselves.
This avoids a root/manifest hash cycle. Typed composition and exact record/collection
digests are recomputed. Primitive payload facts remain declarations.

Selection identifier: `verifier-application-release-selection-1`. Exact fields are
`schema_version`, `root`, `membership_digest`, `source_manifest_digest`,
`source_member_id`, `source_archive_path`, `operation_definitions_digest`,
`contexts_digest`, `requirements_digest`, `artifact_files_digest`, `shards`.
Root has `object_id`, `object_kind` VERIFIER and `record_digest`. Every shard has
`shard_id`, `selection_digest`, `bundle_digest`, `policy_digest`,
`artifact_files_digest`. Caller-selected selection/mechanism pins remain separate.

The membership manifest is `verifier-own-application-membership-manifest-1`:
actual canonical `objects`, `application_root`, `application_root_digest`,
`membership_envelope_id`, `membership_envelope_digest`, `collection_digest` and
retained source/operation/context references. Carried status and counts supply no
acceptance. The source member commits to `verifier-actual-source-manifest-1`, whose
`source_files` rows contain portable `path`, exact byte `bytes` count and `digest`.
The independently selected archive is decoded without filesystem extraction;
actual central-directory records are bounded before decoder allocation, and
every entry must equal the exact source set and its selected bytes. This version
supports stored/deflated single-disk archives; ZIP64 and other compression are
unavailable within this contract. A manifest hash
alone is insufficient. Linked, encrypted, duplicated or substituted entries fail.

Source modules are DATA members, separately from registered checker-interface
VERIFIER records. Operation definitions are syntactic or registered declarations,
not certified public execution operations. Context rows bind exact operation,
instruction and context revision digests. Complete instruction/environment closure,
trusted historical execution and model/agent loaded context are separate evidence.
Observed invocations do not silently declare an operation absent from the pinned
operation definitions. Missing declarations, generation or context evidence remain
unresolved, never inferred.

Requirements identifier: `verifier-application-required-instances-1`. Fields are
`schema_version`, `root`, `tiers`, `instances`. Each instance has `instance_id`,
`object_id`, `operation_id`, `context_digest`, `instruction_digest`, `generation`,
`shard_id`, `node_id`, `tier`, `semantic_version`, `objective`,
`proposition_digest`, `request_digest`, `checker_policy_digest`. Exact native
subject, member records, policy required-object digests and per-node claim, request
and checker-policy bytes must match the selected application records and instance.
Available global contradictions are inspected before missing inputs or cancellation. Every selected instance appears exactly once among
all ten tier rows (`tier`, `census`, `required_instances`). COMPLETE requires a
nonempty exact list; UNKNOWN does not authorize inapplicability. Each instance
maps to one selected native node; extras fail and missing evidence remains UNKNOWN.
These finite lists do not authenticate a complete mandatory application census.

Shard inputs use exact selection/bundle/policy bytes and `artifact_paths` into the
captured immutable file map. Actual `assess_tier_progression` replays each shard.
Per-shard512-node limits remain capacities, never the application's denominator.
Known native FAIL is retained across later missing shards, interruption or exhaustion.
Native finite results remain nested evidence, separate from the release verdict.

Assessment identifier: `verifier-application-release-assessment-2`. It binds exact
`selection_digest`, supplied `expected_selection_digest` and
`expected_mechanism_digest` (null when absent), and the validated closed selected
`root` descriptor. These bindings survive missing input, replay outage and report
compaction. Assessment version 1 remains historical under its original source;
missing bindings are not wildcards and no assessment is silently upgraded. Diagnostic
`binding_status` and `native_status` are separate. `full_gates` reports the five
mandatory unresolved gates. Overall status is FAIL on known refutation, otherwise
UNKNOWN in this version. `polished` and `release_authorized` remain false; full
application status and operational certificate completeness remain UNKNOWN.
CLI UNKNOWN exits2; FAIL exits1. Existing artifact builds retain build-only meaning.

CLI reads explicit selection/member/source/operation/context/requirements paths,
an artifact snapshot, and `verifier-application-shard-locators-1` with a `shards`
list. Locator rows use `shard_id`, `selection_path`, `bundle_path`, `policy_path`,
`artifact_paths`; all paths resolve only inside captured artifact bytes. Manifest
locators, commands, credentials and carried code are never executed or followed.

Bounds:16MiB per selected record,128MiB captured artifacts and referenced native
input/replay artifact bytes,128MiB expanded source,8192 source entries,1024 captured files,32
native shards and16384 selected instances/operation/context rows. Namespace and
native limits also apply. Capacities exhaust as UNKNOWN unless a refutation is
already retained. Bounds do not establish arbitrary process or model correctness,
host confinement, universal safety, human acceptance or promotion.
